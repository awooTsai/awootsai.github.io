# 業務提案版健檢核心規則

> 本檔案是 ada-geo-site-audit 的核心規則。
> 沿襲 v7.x 規則並更新至 v8 GitHub-backed 架構。

---

## 1. 報告核心精神

業務提案版健檢的目標：

> **讓客戶感受問題的存在 + 知道 awoo 能解，但不教客戶自己 DIY 修復。**

這是「業務提案工具」，不是「DIY 修復指南」。

### 三大原則

1. **讓客戶感受問題**：用客觀數據呈現缺口，但不過度恐嚇
2. **不鑽技術牛角尖**：技術細節留給專員版，業務版重點是「方向」
3. **保留 awoo 的價值**：不教客戶自己怎麼修，而是讓客戶想要 awoo 來規劃

---

## 2. 三大痛點選題優先順序（v7.2 內容優先）

報告中選擇三大痛點時，依此優先順序：

### 第一優先：內容層問題
- 內容深度不足 / 文章缺位 / 知識主題空白
- 分類頁缺位 / 商品頁差異化不足
- E-E-A-T 訊號弱
- AI 引用結構不完整

### 第二優先：品牌識別訊號
- 首頁 Title 異常（如為「關於我們」、空白）
- 重要頁 H1 缺失或為 og-fallback
- llms.txt 缺席
- Organization Schema 未設置

### 第三優先：AI 引用結構
- AIO 知識型 vs 品牌推薦型的落差
- Meta Description 多樣性低
- FAQ Schema 缺位

### 不放在三大痛點的項目（業界基礎，僅輔助說明）
- 圖片 Alt 覆蓋率（放灰色提示框即可）
- 純技術項目（cross-canonical、JS 渲染）—— 除非嚴重影響 AI 可讀性

## 3. 觀察判斷標準

### 業務提案版判斷閾值

| 指標 | 業務提案應提出 | 判斷說法 |
|------|--------------|---------|
| Title 多樣性 < 90% | ✅ 提出 | 「大量頁面疑似使用模板化標題，差異化不足」 |
| Meta Description 多樣性 < 70% | ✅ 提出（高優先） | 「多個頁面共用相似描述」 |
| Meta Description 覆蓋率 < 85% | 視情況提出 | 「部分頁面缺少 Meta Description」 |
| H1 含 og-fallback > 10% | ✅ 提出 | 「主標題疑似透過系統補位」 |
| 多重 H1 出現在重要頁 | ✅ 提出 | 「同時存在多個 H1」 |
| 首頁 Title 異常（如「關於我們」） | ✅ 必提（最高優先） | 「首頁標題疑似非品牌名稱」 |
| Schema 覆蓋率 < 80% | 視情況提出 | 「結構化資料覆蓋率有提升空間」 |
| llms.txt 不存在 | 提出（中等優先） | 「目前未偵測到 llms.txt」 |

### 業態相關判斷

詳見 `_shared/industry-patterns.md` 對應段落，找出該業態的「高風險訊號」優先處理。

## 4. 報告結構框架

業務提案版健檢的標準三段式：

```
1. 客觀現況觀察（強項先說）
   → 點出技術基礎已備、Schema 完整等亮點
   → 用綠色 strength banner 強化
   → 不要一上來就罵客戶

2. 三大痛點（內容優先）
   → 痛點 1：內容層問題（最高優先）
   → 痛點 2：品牌識別訊號問題
   → 痛點 3：AI 引用結構問題
   → 每個痛點需有：問題描述 + 對 AI 的影響 + 可驗證的範例頁面

3. 三段同行的方向（GEO 路線）
   → 立竿見影（H1 補強、FAQ Schema、特定關鍵字優化）
   → 中期投資（知識→品牌推薦語意銜接）
   → 長期品牌資產（llms.txt、E-E-A-T、外連策略）
```

每個痛點 problem-card 需包含：
- 問題描述（觀察語言）
- 可驗證範例頁面（已 web_fetch 驗證）
- 對 AI/搜尋引擎的影響說明
- 可選：對應的優化方向（簡述，不深入細節）

## 5. 評估等級與 Hero 區塊

### 評估等級鐵律
- **業務提案版健檢一律僅評估到 🌱 起步期**
- 不寫「成長期」「茁壯期」「領先期」
- 不寫「(推測)」括號標註

理由：避免客戶覺得自己已成長期 → 不需要 awoo 服務。

### Hero 三大數字選擇邏輯

選擇 3 個對客戶最有衝擊力的數字：
- 1 個展示問題（紅色，數字大）
- 1 個展示問題（橙色，次強調）
- 1 個展示亮點（紫色，✅ 標示）

讓客戶 5 秒內看到：「我有問題，但也有亮點，能改善」。

## 6. 視覺呈現鐵律

### 強制規則
- 字體最小 15px（任何位置，含 inline style）
- 字串級鐵律：「harvester」「RAG」「chunks」不出現在報告
- 技術縮寫第一次出現需加白話括號（H1→頁面主標題）
- footer 統一兩段式（v2026-04-09）

### 視覺一致性
詳見 `_shared/visual-system.md` 與 `geo-site-audit/visual/html-template.md`。

---

## 7. URL 驗證鐵律

### 報告中每個 URL 必先 web_fetch 驗證
- HTTP 200 OK
- 頁面實際可開
- 內容與報告引述一致
- 未驗證的 URL 不可寫進報告

### 特殊規則
- harvester missing_samples 的 URL 是「缺 H1」樣本，不代表可開，禁直接抄用
- cross-canonical 若差異只是尾斜線（/path vs /path/）= 誤報，不能寫進報告
- 必須先 curl/web_fetch 原始碼確認 canonical 真的指向不同網域才算

## 8. 平台合作客戶處理

詳見 `_shared/platform-partners.md`。

關鍵原則：
- SHOPLINE / Shopify / 91APP / Cyberbiz / Wix 是合作夥伴
- 不批評平台、不暗示平台是問題來源
- 不寫「awoo × 平台共創」「嘉惠所有平台商家」
- awoo 角色僅為「對該客戶提供工具/服務」

## 9. 多事業單位（Multi-BU）模式判斷

如使用者上傳的網站體質分析涵蓋 ≥3 個 URL（不同事業單位網站），啟動詢問：
- 是否要做「主報告 + 各 BU 輕量版」？
- 還是「單一品牌深度模式」？

詳見 `geo-site-audit/advanced/multi-bu-mode.md`。

## 10. 報告檔名與輸出規則

- 檔名：`{客戶英文名 slug}_geo_{YYYY-MM-DD}.html`
- ASCII only（不含中文、空格、特殊符號）
- 輸出到：`/mnt/user-data/outputs/`
- 用 `present_files` 呈現給使用者
