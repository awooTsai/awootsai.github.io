# 歷史案例教訓

> 過往 awoo 健檢報告踩過的坑與學到的判斷方法。
> 卡關時翻此檔案找答案。

---

## 1. 罕見但高影響的「最高優先問題」

### 1.1 首頁 Title 異常（台全牧場案例）

**情境**：客戶首頁 Title 設為「關於我們」（系統預設）而非品牌名稱。

**判斷**：這是**最高優先問題**，必排第一痛點。

**業務提案版說法**：
> 「您網站首頁的標題（Title）設定疑似為『關於我們』而非品牌名稱。當 AI 引擎掃描網站時，首頁是建立品牌識別的第一入口——目前的設定可能讓 AI 無法正確識別您的品牌主體。」

**範例頁面**：直接列出客戶首頁 URL（已 web_fetch 驗證）。

### 1.2 noindex 涉及知識頁（Cloud Inc 案例）

**情境**：26 頁 noindex 中含廢棄測試商品「55 系列」。

**判斷**：
- 廢棄測試商品 noindex = 合理
- 但需告知客戶「有些頁面被設為不可收錄，建議確認是否包含您希望被 AI 看到的內容」

**業務提案版說法**：
> 「您的網站疑似有 [N] 個頁面被設定為不可被搜尋引擎收錄。建議確認這些頁面中是否包含您希望被 AI 引用的內容。」

### 1.3 FAQ noindex 封鎖（Simmpo 案例）

**情境**：FAQ 頁面被設為 noindex，AIO 機會直接斷線。

**判斷**：FAQ 是 AIO 引用的金礦，noindex 等於放棄 AI 引用機會。

**業務提案版說法**：
> 「您網站的 FAQ 內容疑似被設定為不可收錄。FAQ 內容對 AI 引擎的問答情境引用極為重要，建議確認此設定是否為刻意安排。」

## 2. 罕見的雙品牌 / 多品牌共存

### 2.1 ONE CHILLA 案例（灣沏辣 / 灣泮辣）

**情境**：同一網站有兩個產品線（灣沏辣 / 灣泮辣），但無 llms.txt 說明。

**判斷**：AI 難以精確識別品牌主體，可能混淆兩個產品線。

**業務提案版說法**：
> 「您的網站同時呈現兩個品牌（灣沏辣 / 灣泮辣），但目前疑似缺少 llms.txt（給 AI 看的網站簡介），AI 在識別品牌架構時可能遇到困難。」

## 3. og-fallback H1 問題

### 3.1 Cloud Inc / Simmpo 案例

**情境**：商品頁 H1 為 og-fallback（即從 og:title 讀取，非真實 H1）。

**判斷**：商品識別弱化，AI 無法區分各商品差異。

**業務提案版說法**：
> 「您的商品頁面主標題（H1）疑似透過系統補位（og-fallback），而非為每個商品設置獨立的標題。對 AI 來說，這可能影響它判斷各商品差異的精準度。」

## 4. Cross-canonical 誤報的識別

### 4.1 尾斜線差異 = 誤報

**情境**：harvester 報告 cross-canonical：
```
URL A: https://example.com/page
URL B: https://example.com/page/
```

**判斷**：兩者只差尾斜線 = **誤報**，不可寫進報告。

**確認方法**：
1. 用 curl/web_fetch 取得兩個 URL 的原始 HTML
2. 檢查 canonical 標籤實際指向
3. 若都指向同一網域，就不是 cross-canonical

### 4.2 真實 cross-canonical 的識別

只有當以下條件都滿足才算 cross-canonical：
- canonical 指向**完全不同的網域**（如 a.com → b.com）
- 不只是尾斜線差異
- 不只是 query parameter 差異
- 不只是大小寫差異

## 5. SHOPLINE 客戶的特殊處理

### 5.1 平台識別

確認 SHOPLINE 的線索：
- HTML 中有 `Rendered '*.liquid'` 註解
- `{{ ... | translate }}` 標籤
- 商品 URL 模式：`/products/[slug]`

**注意**：URL 模式單獨判斷不夠（Shopify 也用相同模式），必須結合其他證據。

### 5.2 SHOPLINE 自動產生的內容不該寫成「客戶問題」

- ✅ SHOPLINE 自動 sitemap → 不寫「缺 sitemap」
- ✅ SHOPLINE 商品頁固定模板 → 不寫「商品頁結構過於統一是問題」
- ✅ SHOPLINE 自動 robots.txt → 不寫「robots.txt 設置不當」（除非真的有特殊問題）

## 6. 知識→品牌橋接的觀察套路

### 6.1 Cloud Inc 案例（女性身體議題）

**情境**：89 個 AIO 全是女性身體議題，但品牌推薦型空白。

**業務提案版說法**：
> 「您的網站在 [女性內衣相關身體議題] 的知識型 AIO 表現亮眼，已建立 [N] 個被 AI 引用的關鍵字基礎。但消費者讀完知識後，問 AI『XX 推薦哪家』時，您的品牌尚未建立對應的語意識別——這是『知識→品牌橋接』的明確機會。」

### 6.2 cleanclean 案例

**情境**：知識型 AIO 強，但品牌型空白。

**判斷**：與 Cloud Inc 類似，補強策略：
- 在知識文章中自然置入品牌
- 加入「為什麼選擇 [品牌]」段落
- 文章末尾的 CTA 連結到品牌諮詢/商品頁

## 7. 健檢報告中的「字數深度」判斷

| 字數區間 | 判斷 | 對 AI 引用的影響 |
|---------|------|---------------|
| < 800 字 | 偏短 | AI 引用機率低 |
| 800-1500 字 | 中等 | 基礎引用機率 |
| 1500-3000 字 | 充足 | AI 較容易引用 |
| > 3000 字 | 充足但需結構清晰 | 純堆字反而降低引用 |

業務版說法：
> 「您網站文章的字數深度已具備被 AI 引用的基礎，下一步是強化 H 標籤的層級結構。」

## 8. 卡關時的標準處理流程

當判斷某個觀察「不確定要不要寫」時：

1. **先問**：這個觀察會不會讓客戶覺得「我自己就能 DIY」？
   - 是 → 不要寫進業務版（留給專員版）
   - 否 → 繼續

2. **再問**：這個觀察是否與三大痛點主題相關？
   - 是 → 整合進對應痛點
   - 否 → 放在 specific-issues 體質快覽區塊

3. **最後問**：能否提供可驗證的範例頁面？
   - 是 → web_fetch 驗證後寫進 verified-pages
   - 否 → 不寫進報告

## 9. 罕見業態的查找順序

如客戶業態不在 §1-§5 標準產業中：

1. 先看是否接近某個既有業態（如「健身房」≈ 服務型）
2. 若完全新業態：
   - 找 3-5 個競業網站當參考
   - 人工觀察該業態的常見 SEO 模式
   - 寫進 `_shared/industry-patterns.md` 作為新增段落
   - 1 分鐘後四個 Skill 自動套用
